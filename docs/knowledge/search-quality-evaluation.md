# 検索品質の計測

> **status: Confirmed。** 実装済み。初期ベースラインは #2（全角英数スコアリング欠陥）の修正前に
> 記録しており、全角クエリの低い値は欠陥の数値固定が目的である。

## なぜ要るか

既存のテストはすべて「実装が意図どおり動くか」を見るユニットテストで、**ランキングの良し悪しを
測っていない**。その結果、全角英数がスコアリング語彙から丸ごと脱落する欠陥
（[#2](https://github.com/taito-station/doc-query/issues/2)）が全件 PASS のまま素通りし、実 PDF で
手動検索して初めて発覚した。

**評価集がカバーしない領域には欠陥が残り続ける。** 移植元の `mdq` にも同じ欠陥があるが、そちらの
ゴールデンクエリに**全角英数を含むクエリが 1 件も無い**ため検出されていない
（[vendoring-and-upstream.md](vendoring-and-upstream.md)）。これは仮説ではなく観測である。

**mdq の評価集は日本語を十分に含んでいる**（開発用 40 件中 20 件、ホールドアウト 20 件中 19 件が
日本語クエリ）。それでもこの欠陥を捉えられなかった。**「日本語を入れたから大丈夫」では足りず、
壊れる文字クラスを名指しで入れないと検出できない**——コーパス設計の指針として、この観測を残しておく。

## 指標

ゴールデンクエリ集に対して次を機械算出する。

- **top-1 正解率**: 1 位のヒットが正解である割合
- **top-k 正解率**: 上位 k 件に正解が含まれる割合
- **MRR@k**: 上位 k 件のうち最初の正解の順位の逆数の平均（k 件内に正解が無いクエリの寄与は 0）

**正解判定はヒットのパス一致かつページ範囲（`start_page`〜`end_page` の閉区間）が期待ページを含む
こと。** パス一致のみを根拠に正解としない——同じファイルの無関係なページを返しても正解になってしまい、
所在情報を返すというツールの中心的な価値が測れなくなる。

**正解判定の実装は 1 つとする。** 計測スクリプト側で判定を書き直すと、いつの間にか別の基準で測る
ようになる。

## 評価コーパス

**実物の文書はリポジトリにコミットしない**（REQ-D01-004）。`reportlab` で合成 PDF を生成するスクリプトを
置き、**生成元テキストのみをコミットする**。

生成元テキストの形式は「1 ファイル = 1 PDF、ページ区切りは `%%PAGE%%` の単独行」。**期待着地点の
検証（anchor の一意性・ページ番号の妥当性）は、コミットされない PDF ではなく生成元テキストに対して
行う。** `mdq` は期待パスの実ファイルを読んで検証しているが、PDF が手元に無い状態ではそれが成立しない
ためで、生成元を正本に据えることで fail-closed 検証をそのまま維持する。

### 意図的に含める内容

コーパスは**既知の欠陥が数値に出るように**組む。

- `指定席Ａ` / `指定席Ｓ` / `指定席Ｂ` を**別ページに異なる価格で**（#2 の衝突が順位に出る）
- `カテゴリⅠ` / `カテゴリⅡ`（ローマ数字）
- `０５０－３０６６－９６９０`（全角数字と全角ハイフン）。**現状は grep フォールバックで偶然当たる**
  クエリなので、NFKC 後に BM25 経路へ移っても劣化しないことの証拠になる
- `指定席Ａの払い戻し`（和字と全角の混在）。**フォールバックが効かず静かに劣化する経路**
- 半角の型番（`ABC-1200X`）と英語段落（ASCII を分割しない要件の回帰）
- 全ページに出現する語（IDF 平滑化の回帰）

## 開発用集とホールドアウト集

**分ける。** クエリのみ分離し、コーパスは共通とする（別コーパスまで分けると生成元テキストの保守が
倍になる）。規模は開発用 14〜18 件、ホールドアウト 6〜8 件。

分ける理由は、**開発用集だけだと「そのテストに通る正規化」を選んでしまう**から。今後も k1 / b /
語彙単位というランキングの既定値を触る予定があり、その都度この危険がある。

**既定値のチューニング中はホールドアウトの内訳を見ない。** これは機械検査できない運用規律なので、
計測スクリプトの出力を集計 3 値のみに絞ることで守りやすくする。

## ベースライン

記録済みの実測値を `eval/baselines.json` に置き、**下回ったら失敗**とする（ratchet）。

**トークンカウンタ名の一致を先に確認し、違えば即失敗**にする。`tiktoken` の有無で `count_tokens` の
値が変わり、`--max-tokens` の打ち切り位置＝返るヒット数が変わるので、カウンタが違う比較は無意味である。

上回っても**自動でベースラインを更新しない**。更新は明示的な操作とし、**下げる方向の更新は決定ログの
エントリを伴う**。

### 最初のベースラインは #2 の修正前に取る

全角クエリが軒並み外れた低い値が記録されるが、これは「品質が良い」ことの記録ではなく**欠陥を数値で
固定する**ことが目的である。#2 の修正でその値がどれだけ上がったかを示せるようにする。

**この意図を明記しておかないと、後から見た人が「当時はこの品質で受け入れていた」と誤読する。**

### #3-1: ゴールデンクエリによる回帰計測を導入する (2026-08-24) — 採用

#### コンテキスト

`mdq` は `golden-queries.json` と `golden_eval.py` でこの仕組みを持っているが、doc-query へは移植して
いなかった。同じ蒸留モデルを導入した `paddock` も、`mdq` は検索機能だけ持ち込んで評価系は捨てている。

しかし paddock は mdq を**使う側**であり、doc-query は mdq の**兄弟＝作る側**である。ランキングの
既定値を自分で変える立場にあるかどうかが、評価系の要否を分ける。

#### 決定

`mdq` の評価系を移植する。正解判定は「行番号」ではなく「ページ範囲の包含」に読み替える。
コーパスは合成 PDF を生成し、生成元テキストのみコミットする。開発用集とホールドアウト集を分ける。

#### 理由

- **#2 の欠陥は、評価系が無いことの直接の帰結。** 18 件のテストが全件 PASS のまま素通りした。
- **HVE の要求定義（FR-MDQ-08）が同じ規律を課している。** 語彙照合の単位を変える場合、開発用集と
  ホールドアウト集の双方で変更前を下回らないことを確認せよ、という規定がある。doc-query で NFKC
  正規化を入れるのはまさにこの変更にあたる。
- **評価集がカバーしない領域には欠陥が残る。** 上流 mdq に同じ欠陥が残っていることが実例になっている。

#### 却下した代替案

- **`mdq` の `benchmark.py` をそのまま移植する。** 対照群とのトークン比較・p95 レイテンシ・レポート
  出力まで持ち込むことになるが、doc-query が必要としているのは**ランキングの回帰検知**であって
  Skill の存在価値の証明ではない。
- **実物の PDF をコミットして評価コーパスにする。** 実データに近いが、バイナリを抱えることになり、
  日本語の全角を含む適切な PDF を探すコストもかかる。何より実物のコミットは REQ-D01-004 に反する。
- **抽出後のテキストを直接 fixture にして検索層だけ評価する。** 軽いが、抽出 → チャンク化の回帰を
  検出できない。#2 と同じ「評価集の外に欠陥が残る」構図を自分で作ることになる。
- **開発用集だけにする。** 規模的には十分に見えるが、既定値のチューニングで「テストに通る答え」を
  選ぶ危険が消えない。

#### 影響

- `eval/` を新設（生成元テキスト、ゴールデン集 2 種、ベースライン）
- `docq/golden_eval.py` を追加（正解判定の唯一の実装）
- CI に計測ジョブを追加する。ホールドアウトの内訳は出力せず集計 3 値のみとする
- **最初のベースラインは #2 の修正前に取る**（欠陥を数値で固定する。品質の記録ではない）
