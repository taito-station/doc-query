# 文書クラス D01〜D21 レジストリ

HVE（[dahatake/HypervelocityEngineering](https://github.com/dahatake/HypervelocityEngineering), MIT）の
文書クラス **D01〜D21 を番号・名称を変えずに採用**したもの。番号を変えないのは、将来 HVE や
[paddock](https://github.com/taito-station/paddock) の資産を追加移植するときに読み替えを発生させない
ため。**doc-query 固有クラス（D22 以降）は追加しない**（判断と再開条件は [README.md](README.md) の
決定ログ `#1`）。

各文書は frontmatter の `doc_class` で自分のクラスを宣言する。**このファイルがクラス定義の正本**で、
`scripts/check-doc-classes.py` が本ファイルと全文書の宣言の整合を機械検査する。

> このファイル自身には `doc_class` を付けない（クラス定義そのものであってクラス付き文書ではない）。
> [README.md](README.md) も同様に付けない（規約文書であり frontmatter を持たない）。

## frontmatter の書き方

```yaml
doc_class: [D19, D08]   # 正本。第 1 要素が主クラス（その文書の中心的な関心事）
tags: [D19, D08]        # ミラー。doc_class と完全一致させる（checker が強制）
```

- **常にリスト**（単一クラスでも `[D07]`）。単一値とリストの両方を許すと、消費側すべてで型分岐が必要になる。
- **フロースタイル 1 行**で書く。checker を標準ライブラリのみで実装するため。`sources` はブロックスタイル。
- ID は `D` + 2 桁ゼロ埋め。`D1` は不可。
- **`tags` へのミラーは検索のため。** `docq` は frontmatter を検索に使わないので、`doc_class` 単独では
  クラスで絞り込めない。二重管理の drift は checker が防ぐ。

## クラス一覧

`active` = このリポジトリで運用する / `n/a` = 適用外を宣言して閉じる。
「現行」列は `doc_class` に当該クラスを含む文書数で、**checker が実態と突き合わせる**（手書きとの
不一致は CI で落ちる）。

**`active` かつ 0 本のクラスは作らない。** paddock は 3 クラスを active-0 で抱えて恒久 warning を出して
いるが、文書 8 本の規模で恒久 warning を置くと、本物の充足ギャップがそこに埋もれる。運用しないなら
理由と再開条件を書いて n/a で閉じる。

> 表の書式は checker がパースする契約でもある。`| D01 | 名称 | active | 1 |` の 4 列を崩さない
> （崩れた行は「書式が崩れている」として error にする——黙って落とすとそのクラスが「未定義」になり、
> 参照している文書が全部 error になって原因が読めなくなるため）。

## N/A 宣言

適用外を**明示的に閉じる**。「まだ書いていない」と「そもそも要らない」を区別しないと、充足ギャップの
警告が恒久的なノイズになり、本当の欠落が埋もれる。

**N/A クラスを `doc_class` に指定した文書があれば checker はエラーにする**（宣言と実態の矛盾を
放置しない）。解除するときは本表から行を削除し、上の一覧の状態を `active` に変える。

> **この索引表は checker が frontmatter と 1 対 1 で突き合わせる。** 行の欠落・余剰・値の不一致
> （順序違いを含む）はいずれも error。上の一覧の**クラス別集計数**だけでは、主クラスの順序入替や

### #1: D01〜D21 をそのまま採用し、固有クラスを追加しない (2026-08-24) — 採用

#### コンテキスト

HVE の文書クラス体系は企業の業務システムを要求定義するために作られている。paddock は資産の過半
（予測モデル・買い方・検証記録）を受ける器が D01〜D21 に無いとして D22〜D24 を追加した。その判定基準は
「既存クラスへ押し込むと必須項目が総 UNKNOWN になるか」である（例: 統計モデルを D06「業務ルール・
判定表」に入れると「override 承認者」「発効日」「根拠規程」がすべて空欄になる）。

doc-query で器が要るのは 2 つ——「索引・検索・ランキングの仕様」と「検索品質の評価」——だった。

#### 決定

**D01〜D21 を番号・名称を変えずに採用し、固有クラスは追加しない。** 運用するのは 9 クラス、残り 12 は
理由と再開条件を書いて n/a で閉じる。**active かつ 0 本のクラスは作らない。**

#### 理由

paddock の判定基準を 2 つの候補に当てた結果、どちらも既存クラスに収まった。

- **索引・検索・ランキングの仕様**: D08（データモデル・SoR/SoT・データ品質）にチャンクのスキーマ・
  SoT（文書実体）・派生物（索引）・データ品質（テキストレイヤの有無）が埋まる。D19（アーキテクチャ）に
  モジュール分割・依存方向・技術選定・決定記録が埋まる。ランキング定数（k1 / b / IDF 平滑化 / 語彙単位 /
  正規化）は「アーキテクチャ上の設計定数」として D19 に置けば必須項目が空にならない。
- **検索品質の評価**: D17（品質保証・UAT・受入パッケージ）にテスト方針（回帰計測）・テストケース
  （ゴールデンクエリ集）・合否判定（top-1 / top-k / MRR@k とベースライン下限）が埋まる。
  paddock が D24「実験・検証記録／棄却証跡」を切ったのは、backtest が「受入」ではなく継続的な探索実験で
  採否の証跡そのものが資産だからだが、doc-query のゴールデン計測は**受入基準そのもの**なので D17 が素直。

BM25 の 3 定数程度では、paddock が D22 を切った基準（必須項目が総 UNKNOWN になる）を満たさない。

#### 却下した代替案

- **D22「検索ランキング仕様」を切る。** 直感的には収まりが良いが、上記のとおり D19 の必須項目は
  すべて埋まる。クラスを増やすと、将来 HVE / paddock の資産を移植するときに番号の衝突と読み替えが
  発生する（paddock は D22〜D24 を既に別の意味で使っている）。
- **D05 / D18 を active にして SKILL.md の内容を docs へ蒸留する。** `.claude/skills/pdf-query/SKILL.md`
  の USE FOR / WHEN / DO NOT USE は実質ユースケース定義であり、Prompt ガバナンスの資産でもある。
  ただし docs 側へ写すと SKILL.md との二重管理を `sources` 追従で抱えることになり、文書 2 本を増やす
  対価がそれに見合わない。SKILL.md を正本として扱い、再開条件を書いて閉じる。
- **paddock のように active-0 のクラスを残して充足ギャップを可視化する。** 文書 8 本の規模では、
  恒久的に出続ける warning が本物の欠落を隠す側に働く。

#### 影響

- 新規クラスの追加は将来の判断として決定ログに残る。**再開条件**: 学習型・意味検索（埋め込み・
  リランカ）を導入し、素性定義・重み・較正パラメータを持つようになったら D22 相当を再判定する
- n/a 12 クラスはそれぞれ再開条件を持つ。条件に当たる変更を入れる PR は、同じ PR でこの表を直す
- `scripts/check-doc-classes.py` は「n/a クラスを `doc_class` に指定した文書」を error にする
